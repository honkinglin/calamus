# 回放查找基准

运行 `pnpm bench:replay`。脚本先构建核心，再输出 JSON；任一对照输出不一致会直接失败。

比较逐笔查找与播放会话索引，在单笔 100000 点、10000 笔各 10 点两种数据下，分别查询 1%、50%、99% 时间位置。使用整数时间戳排除两种算法已知的小数边界语义差别；小数正确性由回归测试覆盖。

每组先校验完整输出，再预热 5 轮，交替执行两种实现采样 30 轮，记录中位数与 P95。索引建立耗时单独记录，仅一次样本，不能与重复测量中位数直接比较。

此次报告：`benchmarks/replay-lookup-2026-11-16.json`。多笔画三个位置的中位数由约 0.0057/0.0772/0.0597ms 变为 0.0005/0.0074/0.0058ms；单笔长线约持平，50% 位置索引版本略慢。亚毫秒测量受 JIT、调度与 GC 影响，应重复运行看趋势，不设硬性性能门槛。

范围仅限 Node CPU 时间定位与可见数组分配。没有测量 Canvas 重绘、几何生成、GPU、输入延迟或浏览器内存，不能据此宣称实际回放 FPS 提升。索引增加 O(笔画数) 会话内存；后续需继续浏览器端验收。

## 浏览器正确性复查

索引优化后的源码已通过固定读回上下文、DPR 2 的引擎诊断，报告为 `benchmarks/engine-indexed-replay-2026-11-16.json`。两条透明交叉笔画共 1000 点，历史/JSON/PNG/回放结束与取消等 7 项像素对照零差异，暂停稳定且文档未改变。这是正确性检查，不包含逐帧性能测量，也未解决默认上下文历史读回差异。

2026-11-17 新增缓存与原绘制中间帧对照（schema 4），使用相同时间索引输出，在 1x/2x 和 100/100000 顶点预算下检查 5 个阶段。20 项新增对照与原 7 项均零像素差异，见 `benchmarks/engine-intermediate-replay-2026-11-17.json`。此结论限于固定读回上下文及合成透明双笔画，不独立验证时间索引选点，也不是性能测试。

## 回放帧间隔观测

schema 5 追加 `replayTiming`，使用浏览器 rAF 回调时间戳计算相邻间隔，保留原始顺序。窗口从恢复后的首帧到结束（含最终画面恢复），排除暂停；不足两个时间戳时统计为 null。当前合成双笔画、4 倍速、固定读回上下文的一次报告为 `benchmarks/engine-frame-intervals-2026-11-17.json`：67 个样本，中位数约 8.3ms，P95 约 16.7ms，最大 17.5ms。没有预热、多次采样或优化前对照，不设速度门槛，也不代表 GPU 完成、输入延迟或稳定 FPS。真实输入与内存验收仍待补。
